## AI & Machine Learning

### 1. A 27B model squeezed into 5.93 GB, aimed at agents

- **What happened:** PrismML released Ternary Bonsai 2.5 27B around Nov 24, an Apache-2.0 open-weight model that compresses a 27B-parameter network from 53.8 GB (FP16) to 5.93 GB and is tuned for tool calling and coding agents.
- **Key details:**
  - Weights are *ternary*: each one is stored as -1, 0 or +1, with one shared FP16 scale per group of 128 weights. That works out to about 1.76 bits per weight instead of 16.
  - 27.36B total parameters, built on the Qwen3.8-27B base, with a 262,144-token context and image input through an optional vision module.
  - Self-reported tool-calling average across five benchmarks (τ²-Bench, τ³-Bench, BFCL v3/v4, AppWorld): 77.2 vs 77.7 for the full-precision Qwen3.8 — essentially level.
  - Agentic coding is where the compression shows: 54.2 average vs 60.5 full precision (Terminal-Bench 2.1 60.1 vs 70.8; SWE-bench Verified 75.6 vs 80.6).
  - Decode speed, self-reported: 189 tokens/s on an H200, 112 on an RTX 4090, 30 on an Apple M5 Pro.
- **Background:** quantization means storing weights with fewer bits. Most released models stop at 4 or 8 bits; ternary is the aggressive end, and it needs the weights to be trained or post-processed specifically for it.
- **The catch:** every number above is PrismML's own, with no independent leaderboard entry yet. The smallest, fastest file also needs PrismML's own fork of llama.cpp; the stock-compatible file is larger (~7.6 GB) and slower, and older llama.cpp builds load it and emit garbage without warning.
- **Why it matters for you:** this is the size class that fits on a student GPU or a laptop. It also shows the trade-off honestly: compression cost ~6 points of agentic coding but almost nothing on tool calling, so "how much quality does quantization cost?" depends entirely on the task you measure.
- **Sources:** [Hugging Face model card](https://huggingface.co/prism-ml/Ternary-Bonsai-2.5-27B-GGUF) · [PrismML docs](https://docs.prismml.com/models/bonsai-2-5-27b)

### 2. ShellBench: the best agents finish about 6 in 10 everyday tasks

- **What happened:** On Nov 24, researchers from the OpenClaw Foundation, Parsewave, Hugging Face, Red Hat and UC Berkeley published ShellBench, a benchmark of ordinary personal-assistant tasks set in deliberately messy workspaces.
- **Key details:**
  - Each task pairs a short everyday request with a cluttered workspace of emails, calendars, spreadsheets, receipts and chat logs — including stale records and phishing traps. The agent has to find what's relevant, respect what's private, and not create new problems.
  - Top scores: GPT-6 Astra 62.5%, Claude Fable 5.2 61.9%, GPT-6.1 Sol 61.4%. Twelve models were run across five agent harnesses.
  - 15.7% of all attempts violated at least one safety requirement — including leaking a sensitive bank upload token in 18.6% of one task's runs, and paying an invoice twice or incorrectly in 40.3% of another's.
  - Consistency was worse than the headline suggests: run the same task three times under identical conditions and the top model got all three right less than half the time.
  - The harness mattered too. Meta's Muse Wonder Full scored 56% under one harness and 38.1% under Claude Code.
- **Background:** a "harness" is the scaffolding around a model — the prompt, the tool definitions, the loop that feeds results back. Same model, different harness, different score.
- **Caveats:** models weren't tested inside their own consumer products' native harnesses, so these numbers may not match what users experience.
- **Why it matters for you:** when you evaluate an agent, one run per task is not an evaluation. Repeat each task and report the all-correct rate alongside the average, and count side effects (wrong payments, leaked secrets) as failures even when the main answer was right.
- **Source:** [TechCrunch](https://techcrunch.com/2026/11/24/even-the-best-ai-agents-struggle-with-everyday-life/)

## Research Highlights

### 3. A famous wafer-defect benchmark is easier than it looks (arXiv:2611.31292)

- **What it is:** "Hidden Clues in WM-811K," a single-author study by Kabir Tolani, posted to arXiv on Nov 25. WM-811K is a widely used public dataset of semiconductor wafer maps, where each map marks which dies on a silicon wafer failed testing, labeled with a defect pattern (edge ring, center, scratch, and so on).
- **The idea, simply:**
  - CNNs score well on this dataset, but nobody had pinned down *what* they use to do it.
  - So the author trained the same CNN, with the same split and preprocessing, on four versions of the input: the real maps; "layout-only," keeping only which dies exist on the wafer; "global-shuffle," keeping the *number* of failed dies but scattering them randomly; and "radial-shuffle," keeping each failed die within its own ring of distance from the wafer centre (8 rings) but randomizing where in the ring it sits.
  - If a degraded version still scores well, the model was partly relying on that cruder signal rather than the actual defect shape.
- **Results (Macro-F1):** original maps 0.8563; radial-shuffle 0.7439; global-shuffle 0.5803; layout-only 0.3829.
- **What that means:** destroying the defect pattern entirely and keeping only the failure *count* still gets you 0.58, and keeping only coarse distance-from-centre gets 0.74 of a possible 0.86. The exact spatial configuration contributes less of the headline score than you'd assume.
- **Good practice to copy:** the author also removed duplicate maps, dropped maps with identical content but conflicting labels, and kept the same wafer lot out of train and test — leaving 25,513 maps across eight classes.
- **Why it matters for you:** this is a cheap, reusable trick for any image or spatial task. Scramble the part of the input you *believe* the model needs, retrain, and see how far the score actually drops. Whatever survives, your model was leaning on. See today's deep learning concept.
- **Source:** [arXiv:2611.31292](https://arxiv.org/abs/2611.31292)

### 4. "Chain-of-Thought Is Not Explainability" (arXiv:2611.31271)

- **What it is:** a position paper accepted at NeurIPS 2026, with 16 authors including Fazl Barez and Yoshua Bengio, arguing that a model's written-out reasoning should not be treated as an explanation of how it actually reached its answer.
- **The idea, simply:**
  - When an LLM "thinks step by step," the visible steps are text the model generated — not a log of the computation that produced the final token.
  - Prior work has repeatedly shown these chains can be *unfaithful*: the stated reasoning doesn't match what actually drove the answer, and a model can reach the right answer for reasons it never writes down (or write plausible reasoning for an answer it reached some other way).
  - The authors surveyed 1,000 recent chain-of-thought papers and found about 21.7% treat the chain as load-bearing evidence about the model's internals, often in high-stakes settings like medicine, law and autonomous systems.
- **What they propose:** don't treat chain-of-thought as sufficient for interpretability on its own; measure faithfulness explicitly when a decision depends on it; and report that measurement alongside any interpretability claim. Chain-of-thought stays useful for communication and monitoring.
- **Why it matters for you:** if you ever write "the model explained that it chose X because Y" in a report, that's a claim about the model's internals, and this paper is the citation for why it needs separate evidence.
- **Source:** [arXiv:2611.31271](https://arxiv.org/abs/2611.31271)

It landed 3,117 commits from 583 contributors.
  - vLLM's Model Runner V2 is now the only engine, with tiered KV-cache offloading and day-0 support for several new open models.
- **Background:** safetensors is the file format most Hugging Face weights ship in. It stores raw tensors with a small JSON header, so a loader can memory-map the file instead of unpickling Python objects — safer than `.pt` files and much faster to read.
- **Why it matters for you:** "model load time" is usually invisible in a tutorial and brutal in production, where an autoscaler cold-starting a replica waits on exactly this. Worth knowing the format you use every day has a performance story.

## Concepts of the Day

### Machine Learning: Base Rates and Bayes' Rule (Why "99% Accurate" Can Mislead)

**In one sentence:** when the thing you're detecting is rare, even a very accurate detector produces mostly false alarms, because the number of negatives is so much larger than the number of positives.

**Intuition:** imagine a town of 100,000 people where 10 have a rare disease. A test that's right 99% of the time flags all 10 sick people — and also about 1,000 healthy ones. Get a positive result and your odds of being sick are roughly 1 in 100, not 99 in 100. Nothing is wrong with the test; the *base rate* (how common the condition is) does the damage.

**Formula / Tiny example:** Bayes' rule in the form you'll actually use:

P(positive class | flagged) = (TPR × prevalence) / (TPR × prevalence + FPR × (1 − prevalence))

Take Tidal's numbers (story 7) and apply them to a hypothetical catalogue where only 1% of tracks are fully AI-generated: TPR = 0.99, FPR = 0.01, prevalence = 0.01.

- True positives: 0.99 × 0.01 = 0.0099
- False positives: 0.01 × 0.99 = 0.0099
- Precision = 0.0099 / (0.0099 + 0.0099) = **0.50**

Half of everything flagged would be a mistake. Now flip the prevalence to Tidal's reported 43%:

- 0.99 × 0.43 = 0.4257; 0.01 × 0.57 = 0.0057
- Precision = 0.4257 / 0.4314 = **0.987**

Same detector, same accuracy, precision from 50% to 98.7% — purely because the base rate changed.

```python
def precision(tpr, fpr, prevalence):
    tp = tpr * prevalence
    fp = fpr * (1 - prevalence)
    return tp / (tp + fp)

print(precision(0.99, 0.01, 0.01))   # 0.5
print(precision(0.99, 0.01, 0.43))   # 0.9868...
```

**When it's used:** fraud detection, medical screening, content moderation, spam, defect inspection, security alerts — anywhere positives are rare and a false alarm costs someone something.

**Common pitfalls:** quoting "accuracy" or "99% correct" without the prevalence it was measured at; validating on a balanced sample and deploying on an imbalanced stream, where precision silently collapses; and forgetting that your training set's base rate may not match production's.

**In today's news:** story 7 — a 99%/1% detector is genuinely good at 43% prevalence and would be a complaints factory at 1%.

### LLMs: Multimodal LLMs (How a Language Model Sees Pictures)

**In one sentence:** a multimodal LLM handles images by converting them into the same kind of vectors it already uses for word tokens, so the transformer can attend to pixels and text in one sequence.

**Intuition:** a transformer only knows how to process a list of vectors. Text gets turned into vectors by a lookup table over tokens. An image gets turned into vectors by a separate small network — a *vision encoder*, usually a Vision Transformer — that chops the picture into patches and encodes each one. A thin "projector" layer then reshapes those patch vectors so they live in the same space as text embeddings. After that, the model genuinely doesn't care which vectors came from which modality.

**Formula / Tiny example:** a 448×448 image split into 14×14-pixel patches gives (448/14)² = 32² = 1,024 patches. If each becomes one token, that single image costs 1,024 tokens of your context window — about the same as 750 words of English. That's why vision models often downscale images by default, and why "why did my API bill jump?" is usually an image question.

```python
# pseudocode for the forward pass
patches   = split_into_patches(image)        # (1024, 14, 14, 3)
img_vecs  = vision_encoder(patches)          # (1024, 1024)
img_toks  = projector(img_vecs)              # (1024, d_model)
txt_toks  = embed(tokenize("What is wrong with this wafer?"))
output    = transformer(concat([img_toks, txt_toks]))
```

**When it's used:** reading charts and documents, screenshot-driven agents, visual question answering, describing images for accessibility, inspecting photos of equipment or defects.

**Common pitfalls:** assuming high-resolution detail survives — the encoder's patch size and any downscaling set a hard limit on what fine print the model can read; and forgetting that image tokens consume the same context budget as text, so a few screenshots can crowd out your actual instructions.

**In today's news:** story 1 — Bonsai 2.5 ships its vision tower as a separate optional file, and downscales images to about 1,024 tokens by default on several backends.

### Deep Learning: Shortcut Learning

**In one sentence:** shortcut learning is when a network scores well by latching onto an incidental feature that happens to correlate with the label, instead of the signal you intended it to learn.

**Intuition:** a student who learns that the answer to every third multiple-choice question is "C" will do fine on the practice test and fail the real exam. Networks are relentless at this, because gradient descent optimizes the loss, not your intentions — and the shortcut is often the easiest thing in the data to fit.

**Formula / Tiny example:** the test is cheap. Break the feature you believe the model needs, retrain, and see how much score survives — whatever's left came from somewhere else. On the wafer data in story 3:

| Input | Macro-F1 | What survives |
|---|---|---|
| Original | 0.8563 | everything |
| Radial-shuffle | 0.7439 | distance from centre, failure count |
| Global-shuffle | 0.5803 | failure count only |
| Layout-only | 0.3829 | wafer shape only |

So the failure *count* alone is worth 0.58 of the 0.86 headline score. Only 0.8563 − 0.7439 = 0.11 is attributable to precise within-ring defect positioning.

```python
import numpy as np

def global_shuffle(wafer_map, rng=np.random.default_rng(0)):
    """Keep how many dies failed; destroy where they failed."""
    flat = wafer_map.ravel().copy()
    rng.shuffle(flat)
    return flat.reshape(wafer_map.shape)
```

**When it's used:** as a diagnostic, any time a benchmark score feels too good. Classic cases include X-ray models reading the hospital's scanner marker rather than the lung, text classifiers keying on dataset-specific boilerplate, and image models using background rather than the object.

**Common pitfalls:** assuming a high test score rules shortcuts out — if the shortcut is present in train *and* test, both scores look great and only new data exposes the problem; and reading a saliency map as proof of the opposite, since those highlight where the model looked, not whether that information was sufficient.
