## AI & Machine Learning

### 1. Google opens Genie 4 world model to developers

- **What happened:** On Nov 19, Google made Genie 4, its "world model" that generates interactive environments, available in the Gemini API and Google AI Studio, a day after a consumer launch for some AI Ultra subscribers.
- **Key details:**
  - It streams continuous 720p worlds at 24 frames per second with synchronized audio, from a text prompt, a reference image, or both. You move with the keyboard and can type live prompts to change weather, lighting or objects.
  - Google's post gives no price. PPC Land, reading Google's developer docs, reports about $0.10 per second of output, billed as 240 tokens per frame (5,760 tokens per second at 24 fps). That works out to about $6 for 60 seconds.
  - Per the same docs: sessions cap at 120 seconds, visual stability may degrade after 60–90 seconds, a paid API key is required, and the first frame takes about 5–9 seconds.
  - All output carries SynthID, Google's invisible watermark.
- **Background:** A *world model* learns how an environment changes in response to actions, so it can "imagine" the next frame given what you pressed. Google pitches it for prototyping and for training robots and AI agents in simulated settings.
- **The catch:** Pricing and limits come from a third-party reading of the docs, not Google's announcement, and Google hasn't published rate limits.
- **Why it matters for you:** Simulated environments are becoming a standard way to generate training data for agents. At roughly $360 per hour of footage, though, budgeting compute is part of the design.
- **Source:** [Google blog](https://blog.google/innovation-and-ai/technology/developers-tools/genie-4-in-gemini-api/), [PPC Land](https://ppc.land/google-charges-developers-about-10-cents-a-second-for-genie-4-worlds/)

### 2. OpenAI's coding agents now hunt ChatGPT's slowdowns

- **What happened:** On Nov 19, OpenAI described Performance Factory, an internal system where Codex agents automatically investigate performance regressions (things getting slower after a code change) whenever an alert fires.
- **Key details:**
  - Its first workflow ran more than 1,700 investigations and root-caused over 600 cases in just over three months, about 17 investigations a day.
  - In a manual review of 100 root-cause write-ups, 70% were graded accurate. The other 30% needed refinement or didn't fully establish the cause.
  - Each task moves through stages (investigate, root cause, propose fix, engineer review and deploy, agent verifies recovery). Separate "adversarial" agent sessions check the diagnoses and fixes.
- **The catch:** OpenAI says fixing was harder than diagnosing: agent fixes were sometimes overly complex or introduced new bugs. An engineer still reviews and merges every change, and that review step is now the bottleneck.
- **Why it matters for you:** Notice the evaluation habit: they hand-graded a sample of 100 outputs before trusting the system. That is the same move you'd make before deploying any model.
- **Source:** [OpenAI](https://openai.com/index/how-openai-performance-factory-keeps-chatgpt-fast/)

## Research Highlights

### 3. Meta FAIR lets an agent rewrite its own memory rules

- **What happened:** In a Meta AI post dated Nov 17 (Chen et al., announced by Jason Weston), Meta FAIR researchers had an agent improve the instructions that govern its own memory, then trained the improved behavior into the model's weights.
- **Key details:**
  - Base model: Kimi-K2.6. Benchmark: Continual Learning Bench, three tasks (Database, Codebase, Spectrum).
  - Three-task average: no memory 20.4; generic memory prompts 36.1; best human-written prompts 44.6; agent-optimized prompts 56.0.
  - After fine-tuning with LoRA (rank 64) on runs from the optimized prompts, the model scored 43.1 using only the generic prompts. That keeps about 7.0 of the 19.9-point gain, or roughly 35%.
  - Most attempts failed: 37 of 44 generated prompt revisions didn't beat the previous best.
- **The idea, simply:**
  - The agent's only memory is a folder of files. One prompt says what to save after a task ("offload"), another says what to read before the next ("load").
  - A second "meta" agent reads the transcripts, spots where memory use went wrong, and rewrites those two prompts. The best versions are kept.
  - Then the model is fine-tuned so it behaves as if it had the good prompts, even when given plain ones.
- **The catch:** One model, one benchmark, three tasks, and scores are the best observed among candidates. Numbers here come via a secondary write-up (FourWeekMBA) of Meta's post; I couldn't open the original.
- **Why it matters for you:** "Memory" for agents is mostly prompt and file design, which you can experiment with today. See today's LLM concept.
- **Source:** [FourWeekMBA](https://fourweekmba.com/ai-metas-self-taught-memory-moved-35-of-its-gain-into-weights/)

### 4. Branchpoint: exploring every reasonable way to analyze a dataset

- **What happened:** A NeurIPS 2026 workshop poster by Mattias Akke and Linus von Ekensteen Löfgren introduces Branchpoint, a way to use an LLM agent for *multiverse analysis*.
- **Key details:**
  - Multiverse analysis asks: if many analysts made different but defensible choices (which outliers to drop, which controls to include), how much would the conclusion change?
  - Earlier agent-based approaches just re-run an LLM with different prompts, which mostly samples the model's own habits.
  - Tested on datasets from two real "many-analysts" studies, where dozens of human teams analyzed the same data.
- **The idea, simply:**
  - Branchpoint reads the agent's reasoning trace to find the decision points it actually hit.
  - It then "forks" the analysis at each decision and forbids the approaches already tried, forcing genuinely different paths.
  - The authors report more unique defensible analyses per probe, at lower cost than re-running from scratch.
- **The catch:** The abstract gives no numbers, so the size of the gain isn't clear yet.
- **Why it matters for you:** Every analysis you do has hidden forks. Writing down your choices and checking whether results survive alternatives is a habit that makes your work far more credible.
- **Source:** [NeurIPS 2026](https://neurips.cc/virtual/2026/156553)

### 5. A frozen model plus a counter tracks state exactly (arXiv:2611.25211)

- **What happened:** In a cs.LG paper listed Nov 20, Jeonghoon Lee shows how to get exact state tracking (keeping a running tally over a long stream of events) out of a language model whose weights are frozen.
- **Key details:**
  - On two-event windows, a 27B model got 3/100 right when answering directly and 96/100 when it wrote out intermediate steps.
  - With a small trained "selector" on top, a frozen 0.8B model solved 299/299 windows of 43,687 events each.
- **The idea, simply:**
  - Instead of asking the model to hold the running total in its head, the selector reads each event and outputs a small update.
  - An external integer "register" (a plain counter in code) adds the updates up, so nothing gets lost over tens of thousands of steps.
- **Why it matters for you:** A good design pattern: let the model interpret messy inputs, and let ordinary code do the exact bookkeeping.
- **Source:** [arXiv](https://arxiv.org/abs/2611.25211)

- **The catch:** AMD gives no speed or battery numbers. AMD's setup steps are Windows-only; Phoronix says AMD told it Linux works too.
- **Why it matters for you:** An OpenAI-compatible local endpoint lets you prototype LLM apps without API bills or sending data off your machine.

## Concepts of the Day

### Machine Learning: Decision Trees

**In one sentence:** A decision tree predicts by asking a sequence of yes/no questions about features ("age > 30?"), each answer leading to the next question until it reaches a leaf with a prediction.

**Intuition:** It's a game of 20 Questions. Good questions split the possibilities into groups that are as "pure" as possible, so you reach the answer fast.

**Formula / Tiny example:** Trees choose splits using *Gini impurity*, Gini = 1 − Σ pₖ², where pₖ is the share of class k in a node.
- Parent node: 6 "yes", 4 "no" → 1 − (0.6² + 0.4²) = 1 − 0.52 = **0.48**.
- Split into left (5 yes, 0 no) → Gini 0, and right (1 yes, 4 no) → 1 − (0.2² + 0.8²) = **0.32**.
- Weighted child impurity = 0.5×0 + 0.5×0.32 = 0.16. Impurity drop = 0.48 − 0.16 = **0.32**, so this split is a good one.

```python
from sklearn.tree import DecisionTreeClassifier, export_text
tree = DecisionTreeClassifier(max_depth=3, min_samples_leaf=20).fit(X_train, y_train)
print(export_text(tree, feature_names=list(X_train.columns)))
```

**When it's used:** Credit and medical rules that must be explainable; and as the building block of random forests and gradient boosting, which dominate tabular data.

**Common pitfall(s):** An unlimited tree memorizes the training data (overfits); limit `max_depth` or `min_samples_leaf`. Small changes in data can produce a very different tree, so don't over-read a single tree's structure.

**In today's news:** Branchpoint (story 4) treats an analysis as a tree of decisions and forks at each branch, the same shape as a decision tree.

### LLMs: Memory for LLM Agents

**In one sentence:** Agent memory is any way of saving information from past steps outside the model's context window and loading the relevant parts back in later.

**Intuition:** A student can't remember every lecture word for word, so they keep a notebook. What matters is what they choose to write down and when they look it up.

**Formula / Tiny example:** Say an agent has a 128,000-token context window and has done 50 past tasks of 4,000 tokens each: 50 × 4,000 = 200,000 tokens, which won't fit. If after each task it saves a 300-token summary, all 50 notes take 15,000 tokens, about 12% of the window.

```python
notes = []
for task in tasks:
    context = load_relevant(notes, task)        # "load" step
    result, transcript = agent.run(task, context)
    notes.append(summarize(transcript, 300))    # "offload" step
```

**When it's used:** Coding agents that keep project notes, customer-support bots that recall past tickets, research agents that track what they've already tried.

**Common pitfall(s):** Saving everything just moves the problem: retrieval then pulls in noise. And stored notes can be wrong or stale; an agent will trust a bad note as much as a good one.

**In today's news:** Meta FAIR (story 3) improved exactly these offload and load rules, lifting scores from 44.6 to 56.0.

### Deep Learning: Diffusion Models

**In one sentence:** A diffusion model learns to generate data by learning to remove noise, step by step, from a random starting point.

**Intuition:** Take a photo and add static a little at a time until it's pure noise. Train a network to undo one small step of static. To generate, start from pure static and run the "undo" many times.

**Formula / Tiny example:** Noise is added as xₜ = √ᾱₜ · x₀ + √(1 − ᾱₜ) · ε, where x₀ is clean data, ε is random noise, and ᾱₜ shrinks from 1 toward 0 as t grows.
- Let x₀ = 2.0, ε = 0.5, ᾱₜ = 0.64. Then √0.64 = 0.8 and √0.36 = 0.6, so xₜ = 0.8×2.0 + 0.6×0.5 = 1.6 + 0.3 = **1.9**.
- The network is trained to predict ε from xₜ. If it predicts 0.5 exactly, we recover x₀ = (1.9 − 0.6×0.5) / 0.8 = 1.6 / 0.8 = **2.0**.

```python
loss = F.mse_loss(model(x_t, t), eps)   # train: predict the noise
```

**When it's used:** Image generators like Stable Diffusion, video and audio generation, protein design, and newer "diffusion language models" that write many tokens in parallel.

**Common pitfall(s):** Generation needs many denoising steps, so it can be slow; fewer steps trades quality for speed. Training loss going down doesn't guarantee good samples, so always look at generated outputs.

**In today's news:** Inception's Mercury models (story 8, Also noted) are diffusion language models, which is why they can output more than 1,000 tokens per second.
