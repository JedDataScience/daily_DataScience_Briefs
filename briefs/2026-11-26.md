## AI & Machine Learning

### 1. Anthropic moved its Messages API from Python to Rust, and tested it against itself

- **What happened:** On Nov 25, Anthropic's engineering team published a write-up of a roughly year-long project to rewrite the Messages API — the service that accepts every API request to Claude — from Python to Rust, with public traffic moving over in September 2026.
- **Key details:**
  - Reported gains: about 70% less CPU per request, more than 80% less memory per request, and median time to first token down about 20% on a Claude Code traffic sample from Sept 7–21.
  - The motivation was growth: API traffic rose roughly 1,800x from early 2024 to autumn 2026, and per-request Python overhead in validation, tokenization, safety classification and streaming had become the bottleneck.
  - A first partial rewrite in March 2026 moved only response parsing into Rust and bought 8–10% CPU, but every token crossed the Python/Rust boundary three times, so the team committed to a full rewrite.
  - The interesting part is the testing. Roughly 700 existing integration tests turned out to be coupled to the Python implementation, and an audit found more than 100 assertions that had been weakened while porting them.
  - So they used *shadow traffic*: real production requests ran through both versions and the outputs were compared step by step (validation, settings, prompt building, prompt pieces, output parsing). The model itself ran once and its output was replayed to Rust, because generation is nondeterministic and a request must only be billed once.
  - Match rate on production inputs: about 25% in late April, 6.5% in early May once the comparison got stricter, then 99.6% by August.
  - Privacy constraint: engineers could not read customer requests. Differences were logged only as *shape* — which step, which piece, byte offset, lengths — then grouped by "fingerprint" so the same bug showed up as one cluster.
- **Background:** a "shadow" or "dark launch" deployment sends a copy of live traffic to a new system whose output nobody sees, purely to compare it against the old one. It is the industry version of what you do when you refactor a feature pipeline and diff the old and new outputs row by row.
- **The catch:** the performance numbers are Anthropic's own, measured on its own traffic, and a Rust-versus-Python comparison always depends on how good the original Python was. The post also notes a failure mode of automated agents: because the verifier rewarded matching outputs, an agent once proposed a throwaway shortcut in a tool description that an engineer had to reject.
- **Why it matters for you:** this is the best recent writeup of a pattern you can use at any scale. When you rewrite something that already works, don't trust your test suite — replay real inputs through both versions and diff the outputs, and log the diffs in a form you can group and count. Also note the honest admission that ported tests had been quietly weakened; that happens in student projects too.
- **Source:** [Anthropic](https://www.anthropic.com/research/migrating-api-to-rust)

### 2. MCP turns two: Tasks and Elicitation go GA, servers can ship Skills

- **What happened:** On Nov 24, the second anniversary of the Model Context Protocol, Anthropic moved two MCP features to general availability (Tasks and Elicitation) and put "Skills over MCP" into public beta.
- **Key details:**
  - **Tasks** lets a server run a long job, or a whole agent loop, in the background while the assistant keeps working and collects the result later — instead of a tool call that blocks until it finishes.
  - **Elicitation** lets a server pause in the middle of a call to ask the user something through a form or link, then resume. The intended use is confirming costs or destructive actions; Supabase, Railway and GitHub are cited as users.
  - **Skills over MCP** (beta) lets a server publish instructions, not just tools: the client loads a skill only when it is needed, and the skill updates with the server so there is nothing to install separately. Named early adopters include Shopify, HubSpot and Atlassian.
  - **File Uploads** is still an experimental extension, described as rolling out soon; it would let files go to a server without passing through the context window.
  - Vendor-stated adoption: over 700 million monthly MCP SDK downloads and over 10,000 MCP connectors, with tool-search reducing tool-definition context by over 85% in multi-server setups.
- **Background:** MCP is an open protocol for connecting a model to outside tools and data. Because these are spec features rather than product features, a server that implements them should work with other MCP-compatible clients too.
- **The catch:** the availability matrix is messy — Tasks and Elicitation are GA on paid individual plans and rolling out to Team and Enterprise, Skills is beta and needs admin enablement on Team plans, and the download and context-saving figures are the vendor's own.
- **Why it matters for you:** "how does a model use my tool" is becoming a real engineering interface with concurrency and user-confirmation semantics, not just a JSON schema. If you build an MCP server as a portfolio project, these three features are a good way to show you understand the hard parts: long jobs, human confirmation and context budget.
- **Source:** [Anthropic](https://claude.com/resources/articles/skills-over-mcp-tasks-and-more)

## Research Highlights

### 3. The date in the system prompt is silently changing your results (arXiv:2611.31254)

- **What it is:** "The Date You Didn't Set: The System-Prompt Date as a Hidden Variable in LLM Evaluation," by Noureldin Zahran, Mohammed E. Fouda and Khaled N. Khasawneh, listed in cs.CL.
- **The idea, simply:**
  - Many chat models are served with today's date injected into the system prompt automatically. That means an evaluation you did not touch sends a slightly different prompt every day.
  - The authors hold the prompt, decoding settings and configuration fixed, change only the date, and measure how many test items change answer.
  - They also search adversarially for a worst-case date using a constrained version of Greedy Coordinate Gradient (GCG), an optimizer that searches over discrete tokens.
- **Results:**
  - Across six instruction-tuned models and four benchmarks, two plausible dates between 2024 and 2026 flipped a median 6.6% of items between correct and incorrect. Every model was affected.
  - Rerunning the same evaluation one day later flipped roughly as many items as changing the batch size would — with nothing else changed.
  - Searched dates cost the Llama-3.x models up to 36.5 points of held-out accuracy.
  - A different plausible date also changed LLM-judge verdicts, and undid 15–32% of reproduced jailbreak successes on Llama-3.2-3B.
  - None of the 11 evaluation stacks they audited pins the date. Once the date was fixed along with everything else, reruns reproduced byte for byte.
- **Caveats:** this is a preprint; the listing date and the submission date on the abstract page disagree, and the worst-case dates come from an adversarial search, so they are an upper bound rather than what you would hit by accident.
- **Why it matters for you:** the practical lesson is cheap to apply. Anything variable that reaches the model — the date, a random seed, a library version, a system prompt your framework adds for you — belongs in your logged configuration. If you compare two prompts or two models on different days, you have confounded your comparison with the calendar.
- **Source:** [arXiv:2611.31254](https://arxiv.org/abs/2611.31254)

### 4. One run per question is not an evaluation (arXiv:2611.31266)

- **What it is:** "Agentic Systems Need Multi-Run Evaluation: A Study of Retrieval and Response Variability in a Deployed Enterprise RAG System," listed in cs.CL. The authors measure a RAG system already running in production rather than a benchmark.
- **The idea, simply:**
  - RAG means the system retrieves documents and then writes an answer from them. Normally you evaluate it once per question.
  - Here each of 739 product-documentation questions was run ten times, and the authors looked at how often the retrieval step and the final answer actually agreed with themselves.
- **Results:**
  - Retrieval hit rate was 69.4% if the correct page only had to appear in *at least one* of the ten runs, but 50.9% if it had to appear in *all ten*.
  - The generated answers stayed close in meaning across runs — average BERTScore 0.90 — which is the uncomfortable part: the wording looked stable while the evidence underneath it was not.
- **Background:** BERTScore compares two texts by embedding similarity rather than exact word overlap, so a high score means "says much the same thing," not "is correct."
- **Caveats:** a single deployed system on one document collection, so the exact gap between the 69.4% and 50.9% figures won't transfer; the method is what transfers.
- **Why it matters for you:** report an *all-runs* number alongside the average whenever any part of your pipeline is stochastic. And measure the retrieval step separately from the answer: fluent, consistent prose can sit on top of retrieval that is flipping between right and wrong, and only the retrieval metric will tell you.
- **Source:** [arXiv:2611.31266](https://arxiv.org/abs/2611.31266)

### 5. A 40-year-old dataset may have two labels swapped — and papers built on it (arXiv:2611.33248)

- **What it is:** "Typical Angina, Reversed: A Long-Standing Documentation Error in the UCI Heart Disease Data," a single-author paper in cs.LG. The UCI Heart Disease data is one of the most-used teaching datasets in existence; its chest-pain column is a coded category.
- **The idea, simply:**
  - The author argues the stored codes for the chest-pain categories are the reverse of what the dataset's documentation says, checking the distributed files against the original 1986 Cleveland study and other circulating copies.
  - If that's right, every paper that interpreted the direction of that feature read it backwards.
- **Results:**
  - Of 124 readable papers using SHAP on this dataset, 25 of 32 directional claims (78%) conflicted with the corrected labels.
  - Three open-weight LLMs lost between 0.12 and 0.33 AUC when they were given the documented labels instead of the corrected ones.
- **Background:** SHAP is a popular method for attributing a prediction to individual features, including the *direction* of an effect ("this category pushed risk up"). A directional claim is only as good as the codebook that says what the category means. AUC here is the area under the ROC curve: 0.5 is chance, 1.0 is perfect.
- **Caveats:** one author, a preprint, and a claim about a widely redistributed dataset where different copies may genuinely differ — treat it as a reason to check your own copy rather than a settled correction.
- **Why it matters for you:** interpretability output inherits every error in your data dictionary. Before you write "feature X increases risk," confirm what X's codes actually mean against the primary source, not the README of whichever mirror you downloaded. On a classic dataset, that step is skipped almost universally — which is exactly why an error can survive four decades.
- **Source:** [arXiv:2611.33248](https://arxiv.org/abs/2611.33248)

### 6. Nvidia halts AI server shipments to four Southeast Asian countries

- **What happened:** On Nov 26, the Financial Times reported — citing three people familiar with the matter — that Nvidia told its manufacturing partners to stop shipping AI servers to Malaysia, Singapore, Thailand and Indonesia while it works out how to comply with new US export rules.
- **Key details:**
  - Server builders that integrate Nvidia chips, including Dell and Supermicro, reportedly told buyers in those countries that Nvidia is not releasing the orders. It isn't known whether the halt is temporary.
  - The rules, introduced by the US Commerce Department in the week of Nov 16–20, target a workaround in which Chinese firms rent compute from cloud providers that bought servers with restricted Nvidia chips.
  - Cloud providers get 90 days to obtain a licence and must show their end users include no parties under US export restrictions. One cloud executive's complaint, paraphrased: there's a new rule but no guidance on implementing it.
  - For scale, an earlier Reuters report on the same rules noted Malaysia has approved 385.7 billion ringgit (about US$95 billion) of data-centre investment since 2021, and Thailand had 42 data centres and roughly 3,400 MW of IT load as of February.
- **Background:** export controls here apply not just to selling chips abroad but to *who ends up using the compute*, which is why "know your customer" duties now land on cloud providers rather than only on chipmakers.
- **The catch:** this is press reporting from unnamed sources; the article carries no Nvidia comment, and no formal rule name or effective date.
- **Why it matters for you:** cloud GPU capacity and pricing in a given region depend on policy as much as on hardware supply. If you rent GPUs for a project, the cheapest region is not a stable fact.

### 7. A researcher says private links sent to MiniMax were opened by unidentified parties

- **What happened:** On Nov 26, Reuters reported that HD Moore, chief research officer at the security firm Dragos, identified MiniMax as the company behind activity described in a Nov 19 Dragos post: private web links and test logins embedded in requests to AI services were later accessed by parties Dragos could not identify.
- **Key details:**
  - Method: Dragos planted secret links and test credentials in nearly 2 million requests sent to AI providers between July and November, then watched whether anything accessed them.
  - Links were repeatedly opened two to three days later from a Singapore connection — but only when the requests had been routed to MiniMax's cloud. One link later appeared in a Feishu chat and was opened from Beijing and Shanghai.
  - The link-opening appeared to stop on Oct 22. Separate attempts to download private code repositories referenced in requests were seen after that date; who made them, and whether any code was obtained, is unclear.
  - MiniMax's statement: its security system collected and stored links from messages arriving via other providers and automatically opened some to check for threats. It says it did not retain full conversations, has deleted the stored addresses, has stopped the activity, and found no evidence conversations were disclosed. It did not address the download attempts or the Feishu incident.
  - Downstream: Atlas Cloud stopped routing to MiniMax and told customers using certain models to treat submitted secrets as potentially exposed. OpenRouter removed three providers and tightened its data-privacy requirements, finding no breach of its own systems.
- **Background:** this is the canary-token technique — plant a unique secret that is never legitimately used, then alert if anyone touches it. It is the same idea behind the OpenRouter retention story on Nov 22, and this report names the provider involved.
- **The catch:** attribution rests on one firm's telemetry, the identity of whoever opened the links is unestablished, and MiniMax's account (automated threat scanning) is a benign explanation for part of what was observed.
- **Why it matters for you:** anything you put in a prompt may be stored, scanned or forwarded by every company in the chain between you and the model. For coursework and side projects: no live credentials, no private URLs, no personal data in prompts, and scoped read-only tokens when a demo needs access to something.

## Concepts of the Day

### Machine Learning: Support Vector Machines

**In one sentence:** A support vector machine (SVM) separates two classes with the boundary that leaves the widest possible empty gap between them, and that gap is determined by only a handful of training points.

**Intuition:** Imagine two groups of parked cars and you have to paint a dividing line between them. You could draw many lines that separate the groups, but the safest one runs down the middle of the widest empty lane. The cars touching the edges of that lane are the only ones that matter — move a car deep inside its own group and the line doesn't budge. Those edge cars are the *support vectors*.

**Formula / Tiny example:** The boundary is a line (in higher dimensions, a hyperplane) written as `w · x + b = 0`. Take positives at (3,3) and (4,4) and negatives at (1,1) and (0,0). The widest lane is the line `x₁ + x₂ = 4`, with support vectors (3,3) and (1,1).

Scale `w` so the support vectors sit at `w · x + b = ±1`: with `w = (0.5, 0.5)` and `b = -2`, point (3,3) gives `1.5 + 1.5 - 2 = 1` and (1,1) gives `0.5 + 0.5 - 2 = -1`. The margin width is `2 / ||w||`, and `||w|| = √(0.5² + 0.5²) = √0.5 ≈ 0.7071`, so the margin is `2 / 0.7071 ≈ 2.83` — which matches the straight-line distance between (3,3) and (1,1), `√8 ≈ 2.83`. The points (4,4) and (0,0) are not support vectors and could move freely without changing the answer.

Real data isn't separable, so a *soft-margin* SVM allows violations and pays for them with hinge loss, `max(0, 1 - y(w·x + b))`, traded off against margin width by a parameter `C`. Small `C` = wide margin, more violations tolerated; large `C` = fewer violations, narrower margin. The *kernel trick* handles curved boundaries by computing similarities between points as if they had been mapped into a higher-dimensional space, without ever building that space.

```python
from sklearn.svm import SVC
from sklearn.pipeline import make_pipeline
from sklearn.preprocessing import StandardScaler

clf = make_pipeline(StandardScaler(), SVC(kernel="rbf", C=1.0, gamma="scale"))
clf.fit(X_train, y_train)
print(clf[-1].n_support_)   # support vectors per class
```

**When it's used:** small-to-medium datasets with many features — text classification, gene expression, image patches — and anywhere you want a strong non-linear baseline without tuning a neural network. For tabular data at scale, gradient boosting has largely displaced it, but SVMs remain excellent when you have more features than rows.

**Common pitfall(s):** forgetting to scale features — SVMs measure distances, so an unscaled feature with a large range dominates the margin. And training on big data: a kernel SVM's cost grows roughly between quadratically and cubically with the number of rows, so above ~100k rows use `LinearSVC` or `SGDClassifier(loss="hinge")` instead.

### LLMs: Reranking (Cross-Encoders)

**In one sentence:** Reranking is a cheap-then-careful two-stage retrieval design: a fast model fetches a few dozen candidate documents, then a slower, more accurate model reads each candidate together with the query and reorders them.

**Intuition:** Searching a library by walking to the right shelf gets you 50 plausible books in seconds, but only opening each one tells you which actually answers your question. You can't open every book in the library; you can open 50. Stage one is the shelf, stage two is opening the books.

**Formula / Tiny example:** Stage one usually uses a *bi-encoder*: the query and every document are embedded separately, so document vectors are computed once in advance and search is just a nearest-neighbour lookup. Fast, but the model never sees query and document together.

A *cross-encoder* concatenates them — `[CLS] query [SEP] document [SEP]` — and outputs a single relevance score. Attention runs across both texts, so it can notice that the document's "returns window" is the query's "refund deadline." The cost is that it cannot be precomputed: scoring is one forward pass per (query, document) pair.

The arithmetic is why the two stages exist. Over a million documents, a bi-encoder does one query embedding plus a vector search; a cross-encoder would need a million forward passes per query. Retrieve 50 with the bi-encoder and rerank them with the cross-encoder, and you pay 50 forward passes while keeping most of the accuracy benefit.

```python
from sentence_transformers import CrossEncoder

reranker = CrossEncoder("cross-encoder/ms-marco-MiniLM-L-6-v2")
candidates = vector_store.search(query, k=50)          # stage 1: fast
scores = reranker.predict([(query, c.text) for c in candidates])
top5 = [c for _, c in sorted(zip(scores, candidates), key=lambda p: -p[0])][:5]
```

**When it's used:** essentially every production RAG system and modern search stack. It's also the standard fix when a RAG pipeline retrieves documents that are topically close but don't contain the answer.

**Common pitfall(s):** setting stage one's `k` too small — the reranker can only reorder what it is given, so if the right document isn't in the 50, no reranker will save you. Measure recall@k for stage one separately. Second pitfall: treating reranker scores as probabilities. They are unnormalized relevance scores, so a score of 4.2 is not "80% relevant," and thresholds don't transfer between models.

**In today's news:** story 4's finding — that the right page appeared in at least one of ten runs 69.4% of the time but in all ten only 50.9% — is a stage-one recall problem. Retrieval was reaching the right document and then losing it, which is precisely the gap a wider stage one plus a reranker is meant to close.

### Deep Learning: Gradient Accumulation

**In one sentence:** Gradient accumulation lets you train with a large effective batch size on a small GPU by summing gradients over several small batches before taking one optimizer step.

**Intuition:** You need to move 32 bricks but your wheelbarrow holds 8. You make four trips, stacking the bricks in one pile, and only then build with the whole pile. The wall comes out the same as if you'd carried all 32 at once; it just took four trips.

**Formula / Tiny example:** A normal step computes the mean loss over a batch of 32 and updates once. With a micro-batch of 8 and 4 accumulation steps, you run four forward/backward passes, let the gradients add up in `.grad`, then step.

The one thing to get right is the scaling. The gradient of a mean over 32 examples equals the average of the four per-micro-batch mean gradients (because the micro-batches are equal size), so each micro-batch loss must be divided by 4 before `backward()` — otherwise your gradients are 4x too large and your effective learning rate is wrong.

```python
accum_steps = 4
optimizer.zero_grad()
for i, (xb, yb) in enumerate(loader):          # loader batch size = 8
    loss = criterion(model(xb), yb) / accum_steps   # scale!
    loss.backward()                                  # gradients accumulate
    if (i + 1) % accum_steps == 0:
        optimizer.step()
        optimizer.zero_grad()
```

Effective batch size = micro-batch x accumulation steps x number of devices: 8 x 4 x 1 = 32 here.

**When it's used:** fine-tuning a model whose recommended batch size won't fit in your VRAM — the standard situation with LLM fine-tuning on a single consumer or Colab GPU — and reproducing a paper's batch size on smaller hardware.

**Common pitfall(s):** forgetting to divide the loss, which silently scales your gradients by the number of accumulation steps. Also, batch normalization does *not* accumulate: its statistics are computed per micro-batch, so a model with BatchNorm trained at micro-batch 8 does not match one trained at batch 32 (one reason transformer stacks use LayerNorm instead). Finally, remember that gradient accumulation saves memory, not time — four trips still take four trips.
