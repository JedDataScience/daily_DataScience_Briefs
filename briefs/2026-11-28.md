## AI & Machine Learning

### 1. Sber's GigaChat 4: a 708B open model that runs like a 41B one

- **What happened:** On Nov 26, Sber released GigaChat 4, a family of two models, and published the weights of the larger 708B model on Hugging Face under the MIT license.
- **Key details:**
  - 708B total parameters, about 41B *active* per token (roughly 5.8%). The mixture-of-experts layers have 256 routed experts plus 1 shared expert, and each token uses 8.
  - It uses a hybrid attention design: 48 Gated DeltaNet (linear-attention) layers and 16 MLA layers, interleaved about 3:1. The full layers use sparse attention that picks 2,048 earlier tokens per query. Native context is 1,048,576 tokens (1M).
  - One checkpoint has both a "Reasoning" and an "Instant" mode, plus a built-in multi-token prediction layer for faster generation (see today's LLM concept).
  - Self-reported results (Reasoning mode): SWE-bench Verified 80.89 (GLM-5.3: 86.67), Terminal-Bench 2.0 71.26 (GLM-5.3: 71.67), GPQA Diamond 82.83 (DeepSeek V4 Flash: 91.00), and IFBench 80.33, the top score in its own table.
  - The smaller sibling has 37B total and about 3.8B active parameters. The FP8 708B model is served across two machines with eight 80 GB H100 GPUs each (see today's deep learning concept).
- **Background:** "Linear attention" layers keep a fixed-size memory instead of a growing list of every past token, so long contexts cost less. "MIT license" means you can use, modify and sell products built on the weights as long as you keep the copyright notice.
- **The catch:** every benchmark is Sber's own, and its table shows real gaps: on "Humanity's Last Exam" (text-only, no tools) it scores 23.91 against 37.80 for DeepSeek V4 Flash. The pages we read did not state the 37B model's license.
- **Why it matters for you:** this follows Ant's Ling-3.2-air (yesterday's story 1) with the same recipe: huge total size, small active size, and mostly linear attention. Learn to read a model card for active parameters, attention type and serving hardware, since those decide whether you can actually run it.
- **Source:** [Hugging Face: ai-sage/GigaChat4-708B-A41B](https://huggingface.co/ai-sage/GigaChat4-708B-A41B), [GigaChat blog: GigaChat 4](https://giga.chat/blog/en/posts/gigachat-4)

## Research Highlights

### 2. How small a difference can a forecasting leaderboard actually detect? (arXiv:2611.31619)

- **What it is:** "What a Forecasting Leaderboard Can Establish: Resolution Reporting for Zero-Shot Time-Series Models," by Arya Sikder and Sriram Pillutla, a NeurIPS 2026 workshop paper that trended on Hugging Face Daily Papers on Nov 27.
- **The idea, simply:**
  - A leaderboard ranks models by averaging their scores over a set of datasets. The authors define its *resolution*: the smallest gap between two models that those datasets can reliably detect.
  - Their tool, Vernier, reports that resolution, which entries can't be told apart from the leader, and whether the displayed order changes when someone else submits a model.
- **Results:**
  - GIFT-Eval (97 dataset configurations from 28 underlying datasets, 130 ranked entries) resolves only about 6.2 rank places, while neighbours on the board sit a median 0.91 places apart. No neighbouring pair in its top ten can be separated.
  - Third-party submissions reversed 20 pairs of existing entries without anyone re-running them under one ranking rule. A geometric-mean-of-error rule reversed none.
  - Shortening each model's history window to 512 steps worsened TimesFM-2.5 by 22.2% and Toto by 20.6%, more than the 9.3% spread across the whole top ten.
- **Why it matters for you:** "ranked #3" can mean "statistically tied with #1." Before choosing a model from a leaderboard, check whether the gap is bigger than the noise, and test it on *your* data (see today's ML concept).
- **Source:** [NeurIPS 2026 workshop page](https://neurips.cc/virtual/2026/175015)

### 3. Most published long-horizon forecasting wins are inside the noise

- **What it is:** "Rethinking Long-Horizon Forecasting Leaderboards: Most Published Margins Fall Within the Noise of Their Own Test Set," by Barry Meng, accepted at the same NeurIPS 2026 workshop.
- **The idea, simply:**
  - Benchmarks like ETTh1 slide a forecast window forward one step at a time, so consecutive test forecasts overlap almost completely and are not independent.
  - The paper counts *independent* test points as roughly the test period's length divided by the forecast horizon. With long horizons, that number is tiny.
- **Results:**
  - Of 293 published-scale margins between models, the usual reporting convention calls 99% of them real. A validated estimator of the noise supports only 41%.
  - At a 720-step horizon on ETTh1, Autoformer (a 2021 model) is tied with the newer models that three flagship papers present as their contributions.
- **Why it matters for you:** if your test points are correlated (overlapping windows, repeated users, neighbouring days), you have less evidence than your row count suggests. This one idea will make you a sharper reader of time-series papers.
- **Source:** [NeurIPS 2026 workshop page](https://neurips.cc/virtual/2026/175100)

## Tools & Libraries

### 4. Google tells AI agents to use its MCP servers to reach Gmail and Drive

- **What happened:** In a Nov 25 post, Google said AI agents that access Workspace (Gmail, Drive, Calendar and so on) must connect through its Workspace MCP servers or command-line tool instead of the regular REST APIs, with technical enforcement from Feb 1, 2027.
- **Key details:**
  - Free "Standard" tier: 5,000 MCP requests per project, per product, per day. Some calls count extra: according to TechStackups, a Gmail thread search counts as 10, so that works out to 500 searches a day. Billing for higher usage starts April 1, 2027. Google hasn't published prices.
  - New admin controls let organizations see and revoke which agents have access, require user confirmation for risky actions (sending external email, changing Drive sharing, bulk edits) and read agent activity logs.
  - New terms bar agents from storing raw data permanently, from using Workspace data to train models, and from scraping. Data must be deleted when a user disconnects.
  - TechStackups' reading of the tool list: Gmail's MCP server can search, read and draft, but can't send, reply or forward without special partner access.
  - Ordinary apps that don't involve an AI agent, such as a nightly backup script, are not affected.
- **Background:** MCP (Model Context Protocol) is an open standard for connecting AI models to outside tools and data. A "server" exposes a set of named actions (such as "search threads") that an agent can call.
- **Why it matters for you:** if you're building an agent project that reads email or documents, the plumbing is changing. Platforms are starting to treat AI agents as a separate kind of user, with separate permissions, quotas and audit logs, so design your project around least privilege and keeping as little data as possible.
- **Source:** [Google Workspace blog](https://workspace.google.com/blog/product-announcements/built-for-trust-and-control-new-ai-agent-protections-and-developer-tools-in-google-workspace), [TechStackups](https://techstackups.com/articles/google-workspace-ai-agents-mcp/)

## Concepts of the Day

### Machine Learning: Paired Tests (Is Model A Really Better Than Model B?)

**In one sentence:** a paired test checks whether two models really differ by comparing them on the *same* test cases and asking if the average difference is bigger than chance.

**Intuition:** to compare two runners, you'd race them on the same track on the same day rather than compare times from different races. Pairing removes the noise from easy and hard test cases, because both models face the same ones.

**Formula / Tiny example:** for each of n datasets, compute the difference d = error_B − error_A. Then t = mean(d) / (sd(d) / √n).
- Six datasets, d = [0.02, −0.01, 0.03, 0.00, 0.01, −0.02].
- mean(d) = 0.005, sd(d) ≈ 0.0187, standard error = 0.0187 / √6 ≈ 0.0076.
- t ≈ 0.005 / 0.0076 ≈ 0.65. With 5 degrees of freedom, you'd need |t| > 2.57 for significance at the 5% level (p ≈ 0.54 here). So model A "wins" on average, but this is a tie.

```python
from scipy import stats
stats.ttest_rel(errors_b, errors_a)   # t ≈ 0.65, p ≈ 0.54
```

**When it's used:** comparing models on the same cross-validation folds, A/B tests with before/after measurements, and leaderboards (stories 2 and 3). For accuracy on one test set, McNemar's test is the paired version for right/wrong outcomes.

**Common pitfalls:** (1) Treating correlated rows as independent. If 2,880 hourly test points are scored with a 720-hour horizon, you have about 2,880 / 720 = 4 independent windows, not 2,880 (story 3). (2) Running an unpaired test on paired data, which throws away the pairing and hides real differences.

**In today's news:** stories 2 and 3 find that many leaderboard "wins" don't pass this kind of check.

### LLMs: Multi-Token Prediction

**In one sentence:** multi-token prediction (MTP) trains a language model to guess not just the next token but one or more tokens after it, which can improve training and speed up generation.

**Intuition:** a good reader doesn't only guess the next word; they anticipate where the sentence is heading. MTP adds a small extra "head" that practises looking two steps ahead.

**Formula / Tiny example:** in "the cat sat on the mat," at the word "cat" the main head predicts "sat" and the MTP head predicts "on." Total loss = L_main + λ·L_mtp.
- Main head gives "sat" a probability of 0.5, so L_main = −ln 0.5 ≈ 0.693.
- MTP head gives "on" a probability of 0.25, so L_mtp = −ln 0.25 ≈ 1.386.
- With λ = 0.3: total ≈ 0.693 + 0.3 × 1.386 ≈ 1.109.

At inference, the MTP guess can act as a free draft: the model checks it on the next step and keeps it if correct. If the extra token is accepted 80% of the time, each step yields on average 1 + 0.8 = 1.8 tokens instead of 1.

**When it's used:** DeepSeek popularized MTP in its V3 models, and GigaChat 4 includes one MTP layer that it reuses for several steps ahead (story 1).

**Common pitfalls:** (1) Confusing MTP with speculative decoding: MTP is built into the model and trained with it, while classic speculative decoding uses a separate small draft model. (2) Expecting a fixed speedup: if the guesses are often rejected, the gain shrinks toward zero.

**In today's news:** story 1.

### Deep Learning: Tensor Parallelism (Splitting One Model Across GPUs)

**In one sentence:** tensor parallelism splits each large weight matrix of a model across several GPUs so that a model too big for one GPU can still run, with each GPU computing part of every layer.

**Intuition:** data parallelism gives every worker a full copy of the model and different data. Tensor parallelism is more like a team splitting one large spreadsheet by columns: each person fills in their columns, then they combine the results.

**Formula / Tiny example:** for a layer Y = XW, split W by columns across 2 GPUs.
- X = [1, 2], W = [[1, 0, 2, 1], [0, 1, 1, 3]].
- GPU 1 holds the first two columns and computes [1, 2]. GPU 2 holds the last two and computes [4, 7].
- Stitching them together gives Y = [1, 2, 4, 7], the same as doing it on one GPU.

```python
Y = torch.cat([X @ W[:, :2], X @ W[:, 2:]], dim=-1)   # each half on its own GPU in practice
```

Memory check for story 1: 708B parameters at FP8 (1 byte each) is about 708 GB. Split over 16 GPUs (TP16), that's about 44 GB of weights per 80 GB GPU, leaving roughly 36 GB for the KV cache and activations (before overhead).

**When it's used:** serving and training any model too large for one GPU. It is usually combined with data parallelism and, for mixture-of-experts models, *expert parallelism*, which puts different experts on different GPUs.

**Common pitfalls:** (1) Forgetting the communication cost: GPUs must exchange partial results at every layer, so tensor parallelism works best inside one machine with fast links and slows down across machines. (2) Counting only the weights: long contexts can need as much memory for the KV cache as the weights themselves.

**In today's news:** story 1's 708B model is served with tensor parallelism across 16 GPUs.
