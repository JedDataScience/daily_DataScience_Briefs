## AI & Machine Learning

### 1. Recursive releases Flint, an open coding model built to run locally

- **What happened:** On Oct 21, the startup Recursive released Flint, its first model, with open weights on Hugging Face.
- **Key details:**
  - 39.8B total parameters, about 2.5B active per token (256 experts, 6 picked per token, plus one shared expert).
  - Context window up to 512K tokens, with 256K recommended. Apache 2.0 license.
  - Self-reported scores: 89.7% on SWE-bench Pro v2, 74.2% on SWE-bench Verified, 54.9% on Terminal-Bench 2.1.
  - Over 125 tokens/sec on an M4 Pro MacBook Pro at short contexts, using quantized weights. Recursive says the 4-bit NVFP4 version scores within 0.7 points of the 16-bit one.
  - Recursive says its automated research system, the "Eureka Machine," did much of the design work, and a small team built the model in under four months.
- **Background:** "Active parameters" are the ones that actually run for each token in a mixture-of-experts model. They set the speed. Total parameters set how much memory you need.
- **The catch:** every number comes from Recursive, and no independent leaderboard has tested Flint yet. It also isn't a cheap laptop model: a 48 GB-RAM machine is the suggested setup.
- **Why it matters for you:** A free, offline coding assistant is becoming realistic for students with a well-equipped laptop. The 4-bit trick that makes it fit is today's LLM concept.
- **Sources:** [Crypto Briefing](https://cryptobriefing.com/recursive-launches-flint-local-coding-model/) · [CellCog spec summary](https://cellcog.ai/blog/recursive-flint/)

### 2. AI models helped find "PHP2Shell," two critical bugs in PHP itself

- **What happened:** On Oct 21, PHP released emergency patches for two remote-code-execution flaws (CVE-2026-109618 and CVE-2026-109619) found by security firm Wiz with the help of AI models.
- **Key details:**
  - Severity up to CVSS 9.2 out of 10. The bugs reach back to PHP 5.4, and an attacker needs no login.
  - The bugs are memory-safety errors. When a request crashes from running out of memory, PHP can leave corrupted state behind for the next request to reuse. That can leak passwords and API keys from other users' requests, or let an attacker run their own code.
  - Wiz used Gemini 4 Argon, GPT-5.6 Sol and its own tools to find the bugs, build working attacks on WordPress, Drupal and Joomla, and test the fixes. It says one researcher did in a week what used to take a top team months.
  - Fixed versions: 8.5.12, 8.4.27, 8.3.36 and 8.2.35. Cloudflare said it saw early attacks before the patches shipped.
- **Background:** CVSS is the standard 0–10 severity score for security bugs. "Remote code execution" means an attacker can run their own programs on your server.
- **Why it matters for you:** AI is speeding up bug-finding for both defenders and attackers, so how fast you update matters more each month. If you host a PHP project, update it today.
- **Sources:** [Wiz Research](https://www.wiz.io/blog/php2shell-php-rce) · [BleepingComputer](https://www.bleepingcomputer.com/news/security/php-ships-emergency-patches-for-critical-php2shell-flaws/)

## Research Highlights

### 3. Human-guided AI agents help prove a 31-year-old math conjecture (KLS)

- **What happened:** On Oct 21, Microsoft Research published an account of how Xinzhi Zhang and Zhao Song proved the Kannan–Lovász–Simonovits (KLS) conjecture from 1995, using AI agents steered by humans (arXiv 2610.01447).
- **The idea, simply:**
  - KLS asks how easy it is to cut a high-dimensional "blob" of probability into two pieces. It predicts a simple flat cut is always nearly as good as the best possible cut, within a constant that doesn't grow with dimension.
  - This matters because it controls how fast random-walk sampling algorithms (the family behind MCMC, Markov chain Monte Carlo) explore high-dimensional distributions.
  - Several AI agents explored about 100 lines of attack in parallel while a researcher pruned the dead ends. The key new criterion came out of that search and was applied recursively until the bound became a fixed constant.
- **Results:** two other groups posted proofs building on the same idea, and a Lean 4 formalization (machine-checked proof) has been released. Unguided AI runs with a similar compute budget did not reach the goal.
- **The catch:** the Microsoft post doesn't say the proof has been peer-reviewed or name the AI models used.
- **Why it matters for you:** In this case the humans supplied the direction and the judgment, and the AI supplied fast, broad exploration. That split is a sensible model for how to use AI in your own analysis work.
- **Source:** [Microsoft Research blog](https://www.microsoft.com/en-us/research/blog/solving-a-31-year-old-grand-challenge-in-mathematics-the-kls-conjecture/)

### 4. "Big Claims, Small Margins": LLM graph methods barely beat simple baselines (arXiv 2610.28714)

- **What it is:** a paper by Michal Podstawski, posted Oct 22, that reruns cheap baselines against published "GraphLLM" results. These methods use LLMs to classify nodes in graphs where each node has text, such as papers in a citation network.
- **The idea, simply:**
  - Run simple methods on the same data splits the LLM papers used.
  - **Correct & Smooth** on TF-IDF word counts trails the reported LLM results by a median of just 2.3 percentage points.
  - A plain MLP (a small feed-forward neural network) on frozen e5-large-v2 text embeddings trails by 2.8 points.
- **Problems it found:** some work picked hyperparameters using the *test* set, and one widely used Cora data loader had text and labels misaligned.
- **Why it matters for you:** Always report a simple baseline. If a big model wins by 2 points at 100x the cost, that's the real headline. Picking settings on the test set is a form of data leakage (today's ML concept).
- **Source:** [arXiv](https://arxiv.org/abs/2610.28714)

**Also noted:** A new paper proposes a "feedback contract" for AI agents that tune ML models: the agent sees a validation score only when the gain clears a noise threshold. On a task with zero real gain, agents with exact scores "found" a 0.0157 improvement versus 0.0033 under the contract ([arXiv 2610.28798](https://arxiv.org/abs/2610.28798)). Another paper finds that dropping to a lower precision usually beats adding 2:4 sparsity for faster LLM inference. Sparsity still helps once you're at the lowest precision the hardware supports: a 2:4 FP8 model got 27% higher prefill throughput on an H100 ([arXiv 2610.28947](https://arxiv.org/abs/2610.28947)). A theory paper studies why Muon-style "orthogonalized" optimizer updates suit the curvature of neural-network loss surfaces ([arXiv 2610.28975](https://arxiv.org/abs/2610.28975)).

## Tools & Libraries

### 5. DuckDB 2.0 LTS adds a server mode, triggers and a VARIANT type

- **What happened:** On Oct 21, DuckDB released version 2.0.0 "Cinnamon Teal," a long-term-support (LTS) release supported until at least October 2027.
- **Key details:**
  - **Server mode:** any DuckDB process can now serve its databases to other clients (`CALL quack_serve(...)` on the server, `ATTACH 'quack:host'` on the client). It listens only on localhost by default.
  - **VARIANT type:** stores JSON-like data with mixed shapes in a compressed columnar format, including reading and writing Parquet.
  - **Triggers:** `CREATE TRIGGER` lets the database run SQL automatically when rows change, for example to keep a summary table up to date.
  - **Agent mode** in the CLI gives AI coding agents compact output and cut the text a model had to read by 59% on TPC-H. Reads from S3 and other remote storage now use asynchronous I/O.
- **Breaking changes:** older DuckDB versions can't open database files created by 2.0. Single-arrow lambdas (`x -> x + 1`) are off by default, so write `lambda x: x + 1`. Intel Macs are being phased out.
- **Why it matters for you:** `pip install -U duckdb` gets you the new version. For course projects, the VARIANT type is the bigger change: messy API data no longer needs to stay as raw text.
- **Source:** [DuckDB blog](https://duckdb.org/2026/10/21/announcing-duckdb-200)

### 6. LiteLLM 1.107.0 on PyPI shipped a credential stealer

- **What happened:** On Oct 21, attackers used stolen GitHub tokens from three LiteLLM engineers to publish malicious versions of the library to PyPI and Docker. LiteLLM is a popular Python library that gives one interface to many LLM APIs.
- **Key details:**
  - The bad `litellm==1.107.0` was on PyPI for about 1 hour 44 minutes (11:39–13:23 UTC). The affected Docker tags, including `latest`, were live for about 2.5 hours.
  - The malware added a `cook.pth` file and `sitecustomize.py` that run on *every* Python startup, even `pip`. It steals cloud credentials and API keys and installs a backdoor that waits for remote commands.
  - The official source code was clean. The packages were built from an attacker-controlled copy.
  - **Fix:** don't run `pip install` in an affected environment first. Delete the malicious files, rebuild the environment, pin `litellm==1.106.2`, and rotate every key the machine could reach.
- **Background:** a "supply-chain attack" poisons a package you trust instead of attacking you directly. A `.pth` file in `site-packages` can run code automatically whenever Python starts, which is why it's a favorite hiding spot.
- **Why it matters for you:** Pin your dependency versions (`requirements.txt` with `==`, or a lockfile from `uv` or `poetry`). Keep API keys in a `.env` file or secrets manager with spending limits, never hard-coded in scripts.
- **Source:** [LiteLLM security incident report](https://docs.litellm.ai/blog/security-incident-oct-21-2026)

## Concepts of the Day

### Machine Learning: Data Leakage

**In one sentence:** Data leakage is when information your model wouldn't have at prediction time sneaks into training or model selection, so your evaluation looks better than real-world performance will be.

**Intuition:** It's like a student who saw the exam questions while "practicing." Their practice score is great, but it tells you nothing about how they'll do on a new exam. Any time the test set influences a decision, it stops being a fair exam.

**Tiny example:** You try 20 hyperparameter settings that all have true accuracy 80%, and you score each on the same 200-example test set. Each score has noise: standard deviation = √(0.8 × 0.2 / 200) ≈ 2.8 points. If you pick the *best* of 20 noisy scores, you'll report about **85%** on average (a simulation gives 85.1%), even though nothing is better than 80%. The fix: choose settings on a validation set or with cross-validation, and touch the test set once. Also put preprocessing inside a pipeline so it's fit only on training folds:
```python
from sklearn.pipeline import make_pipeline
from sklearn.preprocessing import StandardScaler
from sklearn.linear_model import LogisticRegression
from sklearn.model_selection import cross_val_score
pipe = make_pipeline(StandardScaler(), LogisticRegression())
print(cross_val_score(pipe, X_train, y_train, cv=5).mean())  # scaler refit per fold
```

**When it's used:** checking for leakage belongs in every project. It's especially easy to miss in time series (future data in training), medical data (the same patient in both train and test) and Kaggle-style competitions.

**Common pitfalls:**
- Scaling, imputing or selecting features on the *full* dataset before splitting.
- *Target leakage:* using a feature that's only known after the outcome, such as "refund issued" when predicting fraud.

**In today's news:** Story #4 found hyperparameters chosen on the test set, and the feedback-contract paper (Also noted) shows AI agents overfitting to validation noise the same way.

### LLMs: Quantization

**In one sentence:** Quantization stores a model's weights with fewer bits, for example 8 or 4 instead of 16, so the model takes less memory and runs faster, at the cost of a little precision.

**Intuition:** It's like rounding prices to the nearest dollar. You lose the cents, but the totals barely change, and the list is much shorter to write down. Neural networks have millions of slightly redundant weights, so they usually tolerate this rounding well.

**Tiny example (symmetric 8-bit):** weights = [0.12, −0.50, 0.31, 0.95]. Scale = max|w| / 127 = 0.95 / 127 ≈ 0.00748. Divide each weight by the scale and round to an integer: [16, −67, 41, 127]. To use them, multiply back: [0.1197, −0.5012, 0.3067, 0.95], so every error is under 0.002.

The memory math for Flint (story #1): 39.8B weights × 2 bytes (16-bit) ≈ **79.6 GB**, but × 0.5 bytes (4-bit) ≈ **19.9 GB**, plus a little extra for the scales. That's the difference between a server GPU and a laptop.
```python
import torch
w = torch.tensor([0.12, -0.50, 0.31, 0.95])
scale = w.abs().max() / 127
q = torch.round(w / scale).to(torch.int8)   # stored
w_hat = q.float() * scale                    # used at runtime
```

**When it's used:** running LLMs locally (GGUF, MLX and NVFP4 files), cheaper cloud serving, and phones.

**Common pitfalls:**
- *Outliers:* one huge weight stretches the scale so all the small weights get rounded to nearly zero. Real methods use a separate scale for each small group of weights.
- Benchmarks are often reported for the full-precision model. Check scores for the quantized version you'll actually run.

**In today's news:** Flint's 4-bit version scores within 0.7 points of 16-bit (story #1), and the 2:4 sparsity paper (Also noted) finds lower precision usually beats pruning for speed.

### Deep Learning: Optimizers (SGD, Momentum and Adam)

**In one sentence:** An optimizer is the rule that turns the gradient (the direction that reduces the loss) into an actual update to the weights.

**Intuition:** Imagine walking downhill in fog. **SGD** takes a step proportional to how steep the ground is under your feet. **Momentum** is like a rolling ball: it builds up speed in directions that stay consistent and smooths out zig-zags. **Adam** also gives each weight its own step size: it shrinks steps for weights whose gradients are large or jumpy and enlarges them for weights with small, steady gradients.

**Formula:** SGD: w ← w − lr · g. Adam keeps running averages m (of g) and v (of g²), then w ← w − lr · m̂ / (√v̂ + ε).

**Tiny example (first step, lr = 0.001, β₁ = 0.9, β₂ = 0.999, g = 0.5):**
- m = 0.1 × 0.5 = 0.05 → bias-corrected m̂ = 0.05 / (1 − 0.9) = 0.5
- v = 0.001 × 0.25 = 0.00025 → v̂ = 0.00025 / (1 − 0.999) = 0.25
- Adam step = 0.001 × 0.5 / √0.25 = **0.001**. SGD step = 0.001 × 0.5 = 0.0005.
- If the gradient were 50 instead, SGD would jump 0.05, but Adam's first step would still be about 0.001. Adam is far less sensitive to gradient scale.
```python
opt = torch.optim.AdamW(model.parameters(), lr=1e-3, weight_decay=0.01)
for x, y in loader:
    opt.zero_grad(); loss_fn(model(x), y).backward(); opt.step()
```

**When it's used:** AdamW is the default for transformers and most deep learning. SGD with momentum is still common for CNNs on images, where it often generalizes slightly better.

**Common pitfalls:**
- Forgetting `opt.zero_grad()`. PyTorch *adds* new gradients to old ones by default, so updates silently grow.
- Reusing a learning rate across optimizers: a good SGD rate (around 0.1) is usually far too large for Adam (around 0.001).

**In today's news:** The Muon theory paper (Also noted under Research) studies a newer optimizer that "orthogonalizes" each update matrix, a step beyond Adam's per-weight scaling.
