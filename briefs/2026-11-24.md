## AI & Machine Learning

### 1. Gemini agent teams find faster quantum algorithms, with machine-checked proofs

- **What happened:** Google DeepMind and Google Quantum AI are promoting a paper (dated Nov 10, featured in DeepMind's blog this week) in which teams of Gemini agents wrote quantum programs inside the Lean 4 proof assistant and formally verified that they are correct and cheaper than published methods.
- **Key details:**
  - Cost is measured as Q·T ("spacetime volume": logical qubits × non-Clifford T gates). Reductions vs the best published baseline: fixed-point arcsin from >1.08×10⁸ to 3.70×10⁵ (>290×; 3,698 T gates on 100 qubits); fusion stopping-power simulation 10.9×; photochemistry 8.08×; a drug-metabolism enzyme (cytochrome P450) 2.49×.
  - For parallel Grover search, the agents cut expected oracle calls by up to 1.22× (find one target) and 2.55× (find all targets).
  - Teams shared verified results in a wiki and swapped unverified ideas in scheduled "conferences." Across the three science applications, 61% of the savings came from ideas within a team, 15% from the wiki and 24% from conferences.
  - An independent checker confirms the agents didn't change the problem statement or sneak in extra axioms. The Lean library and solutions will be open-sourced "shortly."
- **Background:** Lean is a programming language where a proof either compiles or it doesn't, so a "verified" program can't be quietly wrong the way an unchecked LLM answer can.
- **The catch:** Q·T is a proxy for cost. The authors say real resource needs are still far beyond the first fault-tolerant quantum computers, and results depend on how each problem was specified.
- **Why it matters for you:** Pairing a generator (the LLM) with a strict checker is a pattern you can reuse anywhere outputs can be tested automatically, from unit tests to SQL result checks. See today's LLM concept.
- **Source:** [arXiv:2611.09822](https://arxiv.org/abs/2611.09822), [Quantum Computing Report](https://quantumcomputingreport.com/google-deepmind-and-google-quantum-ai-use-lean-4-to-discover-formally-verified-quantum-algorithms/amp/)

## Research Highlights

### 2. "How long will my job run?" A Random Forest beats the LLMs (arXiv:2611.26875)

- **What happened:** Molakalapalli, Wei, Duan, Carter and Huang posted PreRun on Nov 19, a benchmark for predicting how long a deep-learning training or inference job will take before you launch it.
- **Key details:**
  - Data: 801 training-run records and 1,884 inference records (language and vision models) from a GPU cluster, plus 64 text-generation setups each timed in three separate launches.
  - Compared Qwen3.5-9B, GPT-OSS-120B and Claude Opus 5.5 against regression baselines.
  - On 16 held-out generation setups, the open-weight LLMs underestimated latency by 90–99% on average with no examples.
  - Claude's zero-shot mean absolute error was 4.5× that of a Random Forest trained on just 32 configurations. Five labeled examples in the prompt helped a lot, but unevenly across timing targets.
- **The idea, simply:**
  - Write down a job's details (model size, batch size, sequence length, GPU) and ask: can an LLM "reason" its way to a runtime, or do you need data?
  - Small amounts of measured data plus a classic tabular model won easily.
- **The catch:** Results here come from the abstract; the dataset and code will be released only "upon acceptance."
- **Why it matters for you:** Before reaching for an LLM to estimate a number, try a tree model on even a few dozen real measurements. Today's ML concept covers the boosting cousin of Random Forests.
- **Source:** [arXiv:2611.26875](https://arxiv.org/abs/2611.26875)

### 3. Can agents do real lab-science workflows? Not yet (arXiv:2611.22490)

- **What happened:** A 22-author team posted SciWorkBench on Nov 17, a benchmark of real research tasks in biology, chemistry, materials science and physics, drawn from peer-reviewed papers and expert-written scenarios.
- **Key details:**
  - Models ran inside the Claude Code and Codex agent harnesses under one grading protocol.
  - The best agent's mean score was 57.38 (the abstract doesn't give the scale or the other models' scores).
  - Three recurring failure types: turning textbook knowledge into a task-specific procedure, combining evidence across data types (e.g. images plus tables), and correcting their own mistakes mid-workflow.
- **The idea, simply:**
  - Instead of quiz questions, each task covers one or more stages of a real analysis pipeline (plan, process data, analyze, interpret), using a framework checked by domain experts.
- **Why it matters for you:** "Self-correction" and "combining evidence" are the same skills a data science capstone tests. Agents can speed up the steps, but checking the result is still your job.
- **Source:** [arXiv:2611.22490](https://arxiv.org/abs/2611.22490)

## Tools & Libraries

### 4. BigQuery switches to TabFM 1.1 for no-training predictions in SQL

- **What happened:** BigQuery's Nov 23 release notes say version 1.1 of Google's TabFM tabular foundation model is now the default model behind `AI.PREDICT` and `AI.EVALUATE` (still in preview).
- **Key details:**
  - Usage is one SQL call: pass a table of labeled historical rows, a table of new rows and `label_col => 'is_fraud'`. Classification vs regression is inferred from the label's data type.
  - TabFM was trained only on hundreds of millions of synthetic datasets generated from random causal models, then predicts by reading your labeled rows as in-context examples in a single forward pass.
  - Google says it beats tuned standard models on the TabArena benchmark (38 classification and 13 regression datasets, 700–150,000 rows each), but its blogs give the results only as a chart.
  - Same day: a built-in `embeddinggemma-2` embedding model arrived in `AI.EMBED` (preview).
- **Background:** BigQuery auto-updates and can't be rolled back, so the default model under your query can change without you editing any SQL.
- **The catch:** Google itself recommends XGBoost for very large histories, very many features, custom tuning or feature-importance explanations. Accuracy claims are Google's own.
- **Why it matters for you:** Zero-training tabular models are a fast baseline, but if a model version changes silently, log which version produced each prediction so you can compare runs.
- **Source:** [Google Cloud: BigQuery release notes](https://docs.cloud.google.com/bigquery/docs/release-notes), [Google Research: Introducing TabFM](https://research.google/blog/introducing-tabfm-a-zero-shot-foundation-model-for-tabular-data/), [Google Cloud blog: TabFM in BigQuery](https://cloud.google.com/blog/products/data-analytics/tabfm-adds-predictive-ml-to-bigquery/)

## Concepts of the Day

### Machine Learning: Gradient Boosting

**In one sentence:** Gradient boosting builds a strong model by adding many small decision trees one at a time, each trained to fix the errors the current model still makes.

**Intuition:** Think of editing an essay in passes. The first draft is rough; each new pass only targets what's still wrong, and you make modest changes so you don't overcorrect.

**Formula / Tiny example:** For squared error, each new tree fits the residuals (actual − predicted). Targets y = [10, 14, 20].
- Start with the mean: 14.67 for everyone. Residuals: [−4.67, −0.67, 5.33]. MSE = 16.89.
- A one-split tree groups the first two rows (average residual −2.67) and the third (5.33).
- With learning rate 0.5, predictions become [13.33, 13.33, 17.33]. MSE drops to 6.22.

```python
from sklearn.ensemble import HistGradientBoostingRegressor
model = HistGradientBoostingRegressor(learning_rate=0.1, max_iter=300, early_stopping=True)
model.fit(X_train, y_train)
```

**When it's used:** XGBoost, LightGBM and CatBoost win most tabular problems: credit risk, churn, pricing, ranking, and runtime prediction.

**Common pitfalls:** (1) A high learning rate with many trees overfits; lower the rate and use early stopping. (2) Mixing it up with Random Forests: forests average independent deep trees (bagging); boosting adds shallow trees in sequence.

**In today's news:** Story 2's Random Forest beat LLMs at runtime prediction, and story 4 notes Google still recommends XGBoost for large or high-feature datasets.

### LLMs: Multi-Agent Systems (Agent Teams)

**In one sentence:** A multi-agent system runs several LLM agents, each with its own role or attempt, and has them share results so the group solves problems a single agent misses.

**Intuition:** A study group: everyone tries the problem set alone, then compares notes. One person's trick unblocks another's attempt.

**Formula / Tiny example:** If one agent solves a task 30% of the time and attempts were independent, three agents would succeed 1 − 0.7³ = 65.7% of the time. In practice agents sharing one model make correlated mistakes, so the real gain is smaller, which is why sharing ideas and diverse roles matter.

```python
for round in range(R):
    for agent in team:
        candidate = agent.propose(task, shared_notes)
        if verifier(candidate):          # e.g. tests pass, proof checks
            shared_notes.add(candidate)
```

**When it's used:** Coding agents with planner/coder/reviewer roles, research assistants, and search over math or algorithm designs.

**Common pitfalls:** (1) No verifier: agents can agree with each other on a wrong answer. (2) Ignoring cost: N agents means roughly N times the tokens.

**In today's news:** In story 1, 39% of the savings (15% wiki + 24% conferences) came from ideas passed between agent teams, and Lean acted as the verifier.

### Deep Learning: Axial Attention (Attending Along Rows and Columns)

**In one sentence:** Axial attention applies attention along one axis of a grid at a time (first across each row, then down each column) instead of between every pair of cells.

**Intuition:** To understand a spreadsheet cell, read across its row (the other features of that example), then down its column (how that feature looks in other examples), instead of comparing it to every cell in the sheet.

**Formula / Tiny example:** A table with 1,000 rows × 50 columns has 50,000 cells.
- Full attention: 50,000² = 2.5 billion pairs.
- Row attention: 1,000 rows × 50² = 2.5 million. Column attention: 50 columns × 1,000² = 50 million.
- Total 52.5 million, about 48× fewer.

```python
import torch, torch.nn as nn
R, C, d = 1000, 50, 64
x = torch.randn(R, C, d)                        # one embedding per cell
row_attn = nn.MultiheadAttention(d, 4, batch_first=True)
col_attn = nn.MultiheadAttention(d, 4, batch_first=True)
x = x + row_attn(x, x, x)[0]                    # each row is a sequence of 50 cells
xt = x.transpose(0, 1)                          # (C, R, d)
x = (xt + col_attn(xt, xt, xt)[0]).transpose(0, 1)  # each column is a sequence of 1,000 cells
```

**When it's used:** Tabular foundation models (TabPFN, TabFM), image models that attend along height then width, and protein models over multiple sequence alignments.

**Common pitfalls:** (1) Assuming column order matters: in tables it usually shouldn't, so models avoid positional encodings across columns. (2) Forgetting that column attention still scales with rows squared, so huge tables need sampling or row compression.

**In today's news:** Story 4's TabFM alternates row and column attention, then compresses each row to one vector before in-context learning.
