### 2. Claude helps decode Kurt Gödel's shorthand notebooks

- **What happened:** On Nov 13, The Guardian reported that Helsinki logician Jan von Plato used Anthropic's Claude to work through Gödel's mathematical notebooks, which are written in an obsolete German shorthand (Gabelsberger).
- **Key details:**
  - The material: 16 notebooks, about 1,009 pages, from the early 1940s. Human transcription had moved at roughly one page per week.
  - Given von Plato's transcriptions and background books, Claude produced a 650-page explanation in a couple of days and pulled out 663 theorem candidates.
  - Checked in the Coq proof assistant (software that verifies formal proofs step by step): about 400 held as stated, about 200 needed a fix such as an extra assumption, and about 50 were false. All figures are von Plato's.
  - Von Plato says Gödel was "one step away" from proving the independence of the axiom of choice, which Paul Cohen proved in 1966.
- **The catch:** No paper or data has been released, outside logicians haven't reviewed the reconstruction, and Coq can confirm a statement is valid but not whether the idea was Gödel's or Claude's repair. Reports don't say which Claude model was used.
- **Why it matters for you:** This is the right way to use an LLM on a big extraction job: let it propose, then check every output with a strict verifier. The same pattern applies when you use LLMs to label or extract data.
- **Source:** [explainx.ai (summarizing The Guardian)](https://explainx.ai/blog/claude-godel-notebooks-von-plato-663-theorems-coq-what-is-verified-2026) · [Positron Today (The Guardian)](https://positron.today/posts/2026-11-14-ai-helps-reveal-gdels-hidden-mathematical-discoveries/)

## Research Highlights

### 3. Accurate forecasts, wrong price effects (arXiv:2611.15009)

- **What happened:** In a paper listed Nov 13 and accepted to a NeurIPS 2026 workshop, Juwon Hong, Minha Hwang and Venkatesh Shankar test whether tabular and time-series foundation models can tell a retailer what happens to sales if it changes a price.
- **Key details:**
  - On simulated data (where the true price effect is known) and on real retail sales, forecast accuracy did **not** indicate how accurately a model estimated the price effect.
  - Giving tabular foundation models more context improved forecasts but not the estimated price effect.
  - Instrumental variables (a standard economics fix, below) helped only when supplied in a specific form. When confounding was present, adding raw instruments made the error worse for every model tested.
- **The idea, simply:**
  - Forecasting asks "what will sales be?" Causal estimation asks "what would sales be *if I changed the price*?" Different questions.
  - In historical data, prices are often set in response to demand (say, raised during holidays), so price and sales move together for reasons that aren't cause and effect.
  - An instrumental variable is something that shifts price but affects sales only through price, such as a supplier's cost change. It helps separate the true effect from that tangle.
- **Why it matters for you:** A low forecast error doesn't license "what if" conclusions. If a stakeholder asks what a decision will *cause*, you need a causal design, not just a better predictor. Today's ML concept walks through why.
- **Source:** [arXiv: cs.LG new submissions, Nov 13](https://www.arxiv.org/list/cs.LG/new)

### 4. Simple "fingerprints" beat tabular foundation models at table search (arXiv:2611.14697)

- **What happened:** A paper listed Nov 13 by Ali Younes and co-authors builds a benchmark for whole-table embeddings: one vector per table, used to find, deduplicate or match tables in a big data lake.
- **Key details:**
  - They score embeddings on four things: consistency when you only see part of a table, telling different tables apart, robustness to harmless changes, and efficiency.
  - Across 12 methods, lightweight fingerprints built from column names and text were among the strongest.
  - TabPFN and ConTextTab, two strong tabular foundation models, trailed the best fingerprints when their per-cell outputs were simply averaged or max-pooled into one vector.
  - Learning the pooling step instead (with ConTextTab frozen) raised the Spearman correlation between embedding similarity and actual overlap from 0.04 to 0.43–0.50 on synthetic data, with smaller but consistent gains on real data.
- **The idea, simply:**
  - A model can be great at predicting individual rows and still give poor summaries of a whole table.
  - The weak link was how cell-level vectors were combined, not the model itself. Today's deep learning concept covers exactly that step.
- **Why it matters for you:** Always try a cheap baseline before reaching for a foundation model; here the simple one was hard to beat. And when you squash many vectors into one, the pooling choice matters.
- **Source:** [arXiv: cs.LG new submissions, Nov 13](https://www.arxiv.org/list/cs.LG/new)

## Tools & Libraries

### 5. llama.cpp reaches v1.0.0 with a stability promise

- **What happened:** On Nov 13, ggml-org released llama.cpp v1.0.0, along with v1.0.0 of ggml, the tensor library underneath it. llama.cpp is the engine behind many tools that run LLMs on your own laptop.
- **Key details:**
  - Now follows semantic versioning: a major version bump (2.0) signals breaking changes to the public C API, minor versions add features and model support, and patch versions only fix bugs.
  - Cleanup: 35 deprecated functions removed from the public API.
  - New features include FP8 key-value caches (smaller memory use for long chats), a host-memory cache for mixture-of-experts models, and loading GGUF model files split into external shards.
  - llama-server got security fixes (SSRF, CORS, DNS rebinding) and an `/v1/audio/speech` endpoint. NVIDIA, AMD, Qualcomm, Arm, IBM and Intel are adding hardware test machines.
- **Background:** An API is the set of functions your code calls; an ABI is the compiled-binary version of that contract. "ABI stable" means a program built against v1.0 should keep working with v1.x without being recompiled.
- **Why it matters for you:** Version numbers that mean something make it safer to build projects on local models. Get in the habit of pinning versions (e.g. `llama-cpp-python==x.y.z`) and reading the changelog before a major upgrade.
- **Source:** [Unite.AI](https://www.unite.ai/llama-cpp-v1-0-0-sets-api-stability-rules-for-local-ai-tools/) · [Hugging Face blog](https://huggingface.co/blog/ggml-org/llama-cpp-v1)

It also has breaking changes to exporters (they now return an `ExportedModel`) and slims the `[audio]` install extra, so check your pins before upgrading.

## Concepts of the Day

### Machine Learning: Confounding Variables

**In one sentence:** A confounder is a third variable that affects both your input and your outcome, creating a correlation between them that isn't cause and effect.

**Intuition:** Ice cream sales and sunburns rise together, but ice cream doesn't cause sunburn. Hot, sunny weather drives both. If you ignore the weather, you get a misleading story.

**Formula / Tiny example:** A store's weekly price and sales. Normal weeks: $8 → 120 units, $9 → 110. Holiday weeks: $10 → 200, $11 → 190. The store charges more in holidays because demand is high.

```python
import numpy as np
price   = np.array([8, 9, 10, 11])
sales   = np.array([120, 110, 200, 190])
holiday = np.array([0, 0, 1, 1])

np.polyfit(price, sales, 1)[0]            # +30: "raise price, sell more"?!
X = np.c_[np.ones(4), price, holiday]
np.linalg.lstsq(X, sales, rcond=None)[0]  # [200, -10, 100]
```

Ignoring holidays, each extra dollar seems to add 30 units. Adjusting for the holiday flag reveals the real effect: each dollar *loses* 10 units, while holidays add 100.

**When it's used:** Pricing, A/B test analysis, medicine (does a drug help, or do healthier people take it?), policy evaluation, and any time someone asks "what will happen if we change X?"

**Common pitfall(s):** Assuming a model with great predictive accuracy has learned causal effects; it may lean on confounded patterns that predict well but break when you intervene. Also, "controlling for everything" can backfire: adjusting for a variable that is itself caused by the treatment can add bias. Randomized experiments avoid confounding by design.

**In today's news:** Story 3 shows foundation models forecasting sales well but getting the price effect wrong, which is the confounding problem at scale.

### LLMs: The Agent Loop (ReAct)

**In one sentence:** An LLM agent is a model run in a loop: it reasons about what to do, calls a tool, reads the result, and repeats until the task is done.

**Intuition:** Like a cook following a recipe they've never made: read the next step, do it, taste, adjust, and stop when the dish is ready, rather than writing out every move in advance without looking.

**Formula / Tiny example:** ReAct (short for "Reason + Act") alternates *thought → action → observation*:

```python
history = [system_prompt, user_task]
for step in range(max_steps):
    reply = llm(history)                  # thought + chosen action
    if reply.is_final_answer:
        break
    result = run_tool(reply.tool, reply.args)   # e.g. SQL query, web search
    history += [reply, result]            # observation goes back in
```

Cost grows quickly because each step re-sends the whole history. With a 2,000-token start and 500 tokens added per step, five steps send 2,000 + 2,500 + 3,000 + 3,500 + 4,000 = 15,000 input tokens, not 2,000.

**When it's used:** Coding assistants, data-analysis agents that write and run SQL, customer-support bots, and (per story 1) robots, where the "tools" are cameras and motor commands.

**Common pitfall(s):** No step limit or stopping rule, so the agent loops or keeps "fixing" work that was already correct. Trusting tool outputs blindly: web pages and files the agent reads can contain injected instructions (see our Nov 11 concept on prompt injection).

**In today's news:** LangChain (story 6) sells tooling to trace and test these loops, and OpenAI (story 1) is plugging general models into robot control loops.

### Deep Learning: Pooling (Mean and Max)

**In one sentence:** Pooling combines many vectors (or many values in a region) into one by taking their average or their maximum.

**Intuition:** To summarize a class's test results you might report the average score (mean pooling) or the top score (max pooling). Each throws away different information.

**Formula / Tiny example:** Three cell embeddings from a table: [1, 4], [3, 0], [2, 2]. Mean pooling gives [2, 2]; max pooling takes each dimension's largest value, giving [3, 4]. Padding trap: if a fourth slot is just padding, [0, 0], a naive mean gives [1.5, 1.5]. You need a mask:

```python
import torch
x = torch.tensor([[1., 4], [3, 0], [2, 2], [0, 0]])   # last row = padding
mask = torch.tensor([1., 1, 1, 0])
masked_mean = (x * mask[:, None]).sum(0) / mask.sum()  # tensor([2., 2.])
```

**When it's used:** CNNs use max pooling over small image patches to shrink feature maps; sentence-embedding models often mean-pool token vectors; graph and table models pool node or cell vectors into one summary.

**Common pitfall(s):** Forgetting to mask padding tokens, which drags the mean toward zero for short inputs. Assuming pooling is harmless: averaging can wash out the one signal that mattered, and sometimes a learned pooling layer (or attention-based pooling) works much better.

**In today's news:** Story 4 found that simple mean or max pooling of tabular foundation-model outputs gave weak table embeddings, while a learned pooling rule raised similarity correlation from 0.04 to as much as 0.50.
