### 2. Cloudflare opens the weights of its document-extraction models

- **What happened:** On Nov 18, Cloudflare took Clairic out of preview and released open weights on Hugging Face for both Clairic (27B parameters) and a new, smaller Clairic-flash (9B). Both are also hosted on its Workers AI platform.
- **Key details:**
  - Clairic doesn't write free text. You give it a schema (a list of fields like "invoice total" or "due date"), and it fills each field directly. Each field is generated in parallel and stops on its own.
  - Self-reported, on 336 fresh text fields: Clairic got 335 right (99.7%), Clairic-flash 328 (97.6%), the October preview 295 (87.8%), and an OCR-plus-model pipeline 304 (90.5%).
  - Self-reported median latency on that test: 358 ms for Clairic vs 155 ms for Clairic-flash (about 2.3x faster).
  - Price is charged on input tokens only: $0.24 per million for Clairic and $0.10 for Clairic-flash, with both at $0.10 until Dec 1. A request can include up to 4 images or PDF pages.
- **The catch:** All results come from Cloudflare's own internal tests, which it calls "directional guidance," because there's no public benchmark for this kind of extraction yet. The post doesn't state the license.
- **Why it matters for you:** Pulling tables and fields out of PDFs is a huge share of real data work. A specialized open model that returns typed fields with confidence scores is often a better fit than prompting a chatbot and parsing its text.
- **Source:** [Cloudflare blog](https://blog.cloudflare.com/open-clairic/)

## Research Highlights

### 3. Sampling a diverse *set* of LLM answers (arXiv:2611.25003)

- **What happened:** In a NeurIPS 2026 paper submitted Nov 18, Manuel Prada-Corral, Ryan Cotterell, Tim Vieira and two co-authors proposed PoolDPP, a way to sample K answers from a language model that are good *and* different from each other.
- **Key details:**
  - The problem: each sample from an LLM can be good, but ten samples often say nearly the same thing.
  - On ambiguous text-to-SQL questions (the Ambrosia benchmark), PoolDPP improved the precision-recall tradeoff. On open-ended writing, it improved the quality-diversity tradeoff.
  - On grade-school math (GSM8K), it made answer sets more diverse while keeping pass@K about the same.
  - The authors prove the error of their approximation shrinks like 1/N as the candidate pool size N grows.
- **The idea, simply:**
  - A determinantal point process (DPP) is a way of picking a subset that favors high-quality items and penalizes items that are too similar, like choosing a team where each person adds a different skill.
  - Doing this over every possible string is impossible, so PoolDPP first draws a pool of N candidates, reweights them by quality, then picks K from the pool with a DPP, using text embeddings to measure similarity.
- **The catch:** The abstract gives no headline numbers for the empirical gains, so check the paper's tables before relying on the size of the improvement.
- **Why it matters for you:** If you use an LLM to brainstorm, generate test cases or create synthetic data, diversity is often the whole point. See today's LLM concept on pass@k.
- **Source:** [arXiv](https://arxiv.org/abs/2611.25003)

### 4. Splitting a sparse autoencoder into two branches (arXiv:2611.25165)

- **What happened:** In a paper submitted Nov 18, Anh Tien Nguyen, Dimitris Samaras and Mahdi S. Hosseini proposed DualSAE, a sparse autoencoder that separates "interpretable features" from "everything else needed to rebuild the input."
- **Key details:**
  - Tested on two vision datasets and two text corpora with several encoder and autoencoder setups.
  - Average relative gains of about 29% in reconstruction quality and 34% in interpretability, measured by a "monosemanticity" score (how much each feature means one thing).
  - The authors report consistent gains on downstream uses: topic modeling, generating hypotheses, and steering LLMs. The abstract doesn't give numbers for these.
- **The idea, simply:**
  - A normal sparse autoencoder uses one small set of active features both to explain the model and to rebuild its activations, and those goals pull against each other.
  - DualSAE keeps the sparse branch for clean, meaningful features and adds a residual branch that soaks up the leftover detail. An extra loss term keeps the two from overlapping, and they're trained in two stages.
- **The catch:** These are averages across setups reported in the abstract, and no limitations are stated there.
- **Why it matters for you:** Sparse autoencoders are a main tool for looking inside neural networks. Today's deep learning concept explains how they work.
- **Source:** [arXiv](https://arxiv.org/abs/2611.25165)

### 5. Apache Polaris 1.9.0 ships with a safer commit fix

- **What happened:** In the week of Nov 11–18, Apache Polaris 1.9.0 passed its release vote. Polaris is an open-source catalog for Apache Iceberg tables.
- **Key details:**
  - Bug fix: when the result of a table or view commit was unknown (for example, after a network timeout), Polaris could delete metadata files that had just been written. It no longer does.
  - New option to hand authentication to an external system (`polaris.authentication.credential-mode=external`).
  - New optional field on S3 storage settings for how temporary credentials are issued (AWS STS remains the only and default choice).
  - The first release candidate was cancelled over a license-file problem, and the Python package for 1.9.0 wasn't on PyPI yet when the weekly roundup was written.
- **Background:** A *lakehouse* stores data as open files (often Parquet) in cheap cloud storage, with a table format like Iceberg on top so many engines (Spark, DuckDB, Trino) can query it like a database. A *catalog* keeps track of which files make up each table right now.
- **Why it matters for you:** "Unknown commit outcome" bugs are the kind of thing that silently corrupts tables. If you use Iceberg at an internship or job, knowing what the catalog does helps you debug missing or duplicated data.
- **Source:** [DEV Community: Apache Data Lakehouse Weekly](https://dev.to/alexmercedcoder/apache-data-lakehouse-weekly-november-11-to-18-2026-4ndd), [Apache mailing list](https://lists.apache.org/thread/1gvhpzqzlzvlcp4kss2kqzjmyk3xx3ym)

## Concepts of the Day

### Machine Learning: k-Means Clustering

**In one sentence:** k-means splits unlabeled data into k groups so that each point is close to the average (the *centroid*) of its own group.

**Intuition:** Picture placing k pizza shops in a town. Each house orders from the nearest shop, then each shop moves to the middle of its customers. Repeat until no shop wants to move.

**Formula / Tiny example:** The algorithm alternates two steps: (1) assign each point to its nearest centroid; (2) move each centroid to the mean of its points. It tries to minimize *inertia*, the sum of squared distances from points to their centroids. Take six 1-D points: 1, 2, 3, 10, 11, 12 with k = 2. The groups become {1, 2, 3} and {10, 11, 12}, with centroids 2 and 11. Inertia = (1² + 0² + 1²) + (1² + 0² + 1²) = 4.

```python
import numpy as np
from sklearn.cluster import KMeans
X = np.array([[1], [2], [3], [10], [11], [12]])
km = KMeans(n_clusters=2, n_init=10, random_state=0).fit(X)
print(km.cluster_centers_.ravel(), km.inertia_)  # [11. 2.] 4.0 (order may vary)
```

**When it's used:** Customer segmentation, compressing colors in an image, grouping documents by their embeddings, and building quick "prototype" summaries of a dataset.

**Common pitfalls:** k-means uses distances, so features on bigger scales dominate; standardize first. It also assumes roughly round, similar-sized clusters, and it always returns k clusters even when the data has no real groups.

**In today's news:** Story 3 points out that LLM samples tend to "cluster" around one meaning. Clustering sample embeddings with k-means is a simple way to see how many distinct answers you actually got.

### LLMs: pass@k (and Why Sample Diversity Matters)

**In one sentence:** pass@k is the chance that at least one of k generated answers is correct, a standard way to score code and math models.

**Intuition:** If you get three attempts at a quiz question, what matters is whether *any* attempt is right. Three identical guesses are no better than one.

**Formula / Tiny example:** Generate n samples per problem and count c correct ones. The standard unbiased estimate is pass@k = 1 − C(n−c, k) / C(n, k), where C is "n choose k." With n = 10 and c = 3: pass@1 = 1 − 7/10 = 0.30, and pass@5 = 1 − C(7,5)/C(10,5) = 1 − 21/252 ≈ 0.917. Compare that with independent tries at 30% each: 1 − 0.7⁵ ≈ 0.832. If the model always gave the *same* answer, pass@5 would stay at 0.30.

```python
from math import comb
def pass_at_k(n, c, k):
    return 1 - comb(n - c, k) / comb(n, k)
print(pass_at_k(10, 3, 1), pass_at_k(10, 3, 5))  # 0.3 0.9167
```

**When it's used:** Coding benchmarks, math benchmarks, and any setup where you can check answers automatically and pick a correct one (like running unit tests).

**Common pitfalls:** Comparing pass@1 for one model with pass@10 for another. Also, pass@k assumes you can tell which answer is right; in practice you often can't, so pass@1 is closer to real use.

**In today's news:** Story 3's PoolDPP made GSM8K answer sets more diverse while keeping pass@K about the same.

### Deep Learning: Autoencoders and Sparse Autoencoders

**In one sentence:** An autoencoder is a neural network trained to copy its input to its output through a middle layer, so that the middle layer learns a useful summary of the data.

**Intuition:** Summarize a long email in a few notes, then rewrite the email from your notes alone. The better the notes, the closer your rewrite. A *sparse* autoencoder gives you a huge notebook but only lets you use a few entries for each email, so each entry ends up meaning something specific.

**Formula / Tiny example:** An encoder maps input x to a code h, and a decoder maps h back to x̂. The loss is reconstruction error, often mean squared error (MSE). A classic autoencoder squeezes a 784-pixel MNIST digit into 32 numbers (24.5x smaller). A sparse autoencoder does the opposite, making h wider than x, and adds an L1 penalty, λ·Σ|hᵢ|, so most of h is zero. Example: x = [1, 2], x̂ = [0.9, 2.2], so MSE = (0.1² + 0.2²)/2 = 0.025. If h = [0, 0.5, 0, 1.5] and λ = 0.01, the penalty is 0.01 × 2.0 = 0.02, for a total loss of 0.045.

```python
import torch.nn as nn
class SAE(nn.Module):
    def __init__(self, d=512, m=4096):
        super().__init__(); self.enc = nn.Linear(d, m); self.dec = nn.Linear(m, d)
    def forward(self, x):
        h = self.enc(x).relu(); return self.dec(h), h
# loss = ((x_hat - x)**2).mean() + lam * h.abs().sum(dim=-1).mean()
```

**When it's used:** Compression and denoising, anomaly detection (unusual inputs reconstruct badly), and, for sparse autoencoders, finding human-readable "features" inside LLM activations.

**Common pitfalls:** Assuming low reconstruction error means the features are meaningful; a network can rebuild inputs well with messy, mixed features. With too large a λ, many features "die" and never activate.

**In today's news:** Story 4's DualSAE adds a second branch so the sparse features can stay interpretable while the residual branch handles reconstruction.
